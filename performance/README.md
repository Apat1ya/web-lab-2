# Практическая работа №8. Тестирование и оптимизация производительности сайта

## Цель

Получить воспроизводимые исходные показатели книжного магазина, найти слабые
места, выполнить безопасные оптимизации без изменения бизнес-логики и сравнить
результаты до и после.

Измерения ниже выполнены локально 21 августа 2026 года на Node.js 24.13.0 и
PostgreSQL. Это короткий учебный тест, поэтому абсолютные значения зависят от
компьютера и текущей нагрузки системы.

## Нагрузочный тест

Сценарий реализован в `performance/run-performance.js` только средствами
Node.js, без внешних зависимостей. Он проверяет доступность сервера, затем
выполняет:

1. По 10 последовательных запросов к `/`, `/catalog.html` и `/api/books`.
2. По 20 параллельных запросов к тем же трём маршрутам.

Всего выполняется 90 измеряемых запросов. Для каждого ответа полностью
считывается тело. Рассчитываются количество запросов, успешные и ошибочные
ответы, минимум, среднее, p95, максимум, общая продолжительность и примерное
число запросов в секунду. Также сохраняется разбивка по этапам и маршрутам.

По умолчанию используются:

- `BASE_URL=http://localhost:3000`;
- `SEQUENTIAL_REQUESTS=10` на маршрут;
- `PARALLEL_REQUESTS=20` на маршрут;
- `REQUEST_TIMEOUT_MS=5000`;
- результат `performance/results/latest.json`.

Если сервер недоступен, runner сохраняет JSON со статусом
`server-unavailable` и завершается с ненулевым кодом.

## Результаты до и после

Оба замера выполнены одним runner, с одинаковыми параметрами и запущенным
локальным PostgreSQL. Фактические полные результаты сохранены в
`performance/results/before.json` и `performance/results/after.json`.

| Показатель | До | После | Изменение |
| --- | ---: | ---: | ---: |
| Запросы | 90 | 90 | — |
| Успешные / ошибочные | 90 / 0 | 90 / 0 | — |
| Минимум | 0,770 мс | 0,785 мс | +1,95% |
| Среднее | 51,239 мс | 40,659 мс | −20,65% |
| p95 | 117,068 мс | 79,316 мс | −32,25% |
| Максимум | 127,641 мс | 80,141 мс | −37,21% |
| Общая продолжительность | 213,509 мс | 138,262 мс | −35,24% |
| Примерная пропускная способность | 421,528 req/s | 650,938 req/s | +54,42% |

В исходном замере самым медленным был `/api/books`: среднее 63,778 мс и p95
122,261 мс. В повторном замере: среднее 47,231 мс и p95 79,821 мс.

Результат показывает улучшение именно в этих локальных прогонах. Короткие тесты
чувствительны к прогреву Node.js, PostgreSQL и фоновой нагрузке. Кроме того,
runner измеряет ответы трёх URL, но не эмулирует загрузку всех дочерних ресурсов
браузером. Поэтому эффект lazy loading и browser caching нужно дополнительно
проверить в Chrome DevTools/Lighthouse; весь прирост нагрузочного теста нельзя
приписывать только выполненным изменениям.

## Найденные проблемы

- Статика `/assets`, `/js`, `style.css` и `script.js` возвращалась с
  `Cache-Control: public, max-age=0`, поэтому браузер не мог разумно повторно
  использовать её без проверки сервера.
- Изображения карточек загружались сразу, включая элементы вне видимой области.
- YouTube iframe на `about.html` загружался сразу.
- `assets/banner.jpg` был крупнейшим локальным файлом (462,91 KiB), но нигде не
  использовался.
- `/api/books` был самым медленным из трёх проверенных маршрутов. Изменение SQL,
  PostgreSQL и бизнес-логики не входило в безопасный объём этой работы.
- Часть обложек берётся со сторонних доменов; их скорость и доступность не
  контролируются приложением.

## Выполненные оптимизации

- Для изображений карточек на главной и в каталоге добавлены `loading="lazy"` и
  `decoding="async"`.
- Изображения параллакса в первом экране и изображение отдельной книги не
  переведены на lazy loading, чтобы не ухудшать потенциальный LCP-контент.
- Для YouTube iframe добавлен `loading="lazy"`.
- Для `/assets`, `/js`, `style.css` и `script.js` настроен кеш на 7 дней:
  `Cache-Control: public, max-age=604800`. Директива `immutable` не используется,
  потому что имена файлов не содержат content hash.
- HTML получает `Cache-Control: no-cache`, API — `Cache-Control: no-store`.
- Неиспользуемый `assets/banner.jpg` удалён. Объём локальных изображений в
  репозитории уменьшился с 823,65 до 360,74 KiB (на 462,91 KiB). Это уменьшает
  размер репозитория/развёртывания, но не сетевой вес страницы: файл и раньше не
  запрашивался браузером.
- Добавлен отдельный npm-скрипт для периодического повторения теста.

## Повторный запуск

В первом терминале:

```powershell
npm start
```

Во втором терминале:

```powershell
npm run perf:test
```

Проверка другого адреса и сохранение отдельного результата в PowerShell:

```powershell
$env:BASE_URL = "http://localhost:3000"
$env:PERF_OUTPUT = "performance/results/manual.json"
npm run perf:test
```

Для сопоставимых периодических замеров нужно сохранять одинаковые значения
переменных, одинаковый набор данных и по возможности одинаковую нагрузку на
компьютер.

## Ручная проверка Lighthouse

Lighthouse в рамках автоматического прогона не запускался, поэтому его показатели
не выдумывались. Для ручной проверки:

1. Запустить сайт командой `npm start`.
2. Открыть `http://localhost:3000/` в Chrome в режиме инкогнито.
3. Открыть DevTools → Lighthouse.
4. Выбрать категорию **Performance** и режим **Desktop**, запустить анализ.
5. Сохранить значения Performance, FCP, LCP, TBT и CLS (или экспортировать
   отчёт).
6. Повторить анализ в режиме **Mobile** и сохранить те же показатели.
7. Для честного сравнения «до / после» использовать одинаковые настройки Chrome,
   сети и CPU throttling.

## Вывод

Проект получил отдельный воспроизводимый нагрузочный тест и сохранённые реальные
результаты до/после. Без изменения дизайна и бизнес-логики устранены немедленная
загрузка некритичного контента, отсутствие полезного кеширования статики и
крупный неиспользуемый файл. Локальный повторный замер лучше исходного по среднему
времени, p95 и пропускной способности, но browser-level эффект следует отдельно
подтвердить Lighthouse.
